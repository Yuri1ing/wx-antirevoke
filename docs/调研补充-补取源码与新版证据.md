## 1. 【新】iOS 第二条路线：`kelvinhongkjy/WeChat-DenyRevocation`

- 源文件：`Tweak.xm`，**1152 字节**，SHA `042673b0424e5451bd2f2302a782337864294f48`
- 原文 URL：<https://github.com/kelvinhongkjy/WeChat-DenyRevocation/blob/master/Tweak.xm>
- 取法：`https://api.github.com/repos/kelvinhongkjy/WeChat-DenyRevocation/contents/Tweak.xm`

**去掉文件头部的 Logos 模板注释后，全文如下：**

```objc
%hook CMessageMgr

- (void)DelMsg:(id)arg1 MsgList:(id)arg2 DelAll:(_Bool)arg3
{
	/* do nothing */
}

%end
```

**这是 iOS 上第二条、并且技术思路与 itenfay 完全不同的路线：**

| | itenfay/WeChat_tweak | kelvinhongkjy/WeChat-DenyRevocation |
|---|---|---|
| hook 点 | `-[CMessageMgr onRevokeMsg:]` | **`-[CMessageMgr DelMsg:MsgList:DelAll:]`** |
| 时机 | 撤回**系统消息**到达时 | 本地**执行删除**时 |
| 手法 | 不调原实现，伪造 `msgType 0x2710` 的 tip 用 `AddLocalMsg:` 插回 | **方法体置空**，什么都不做 |
| 结果 | 消息留下 + **一条自定义提示** | 消息留下 + **原生"对方撤回了一条消息"照常显示** |
| 依赖 | 强依赖 `<session>` / `<replacemsg>` / CDATA 文本格式 | **不解析任何内部文本格式**，只挡删除动作 |

仓库 README 原话（<https://github.com/kelvinhongkjy/WeChat-DenyRevocation/blob/master/README.md>）：
> "When someone is trying to revoke his/her message, you will see a bubble indicating his/her attempt below the message he/she is trying to revoke."

**风险评估（我的推断，非仓库声明）**：`DelMsg:MsgList:DelAll:` 是**消息删除的通用入口**，不只是撤回会走。整个方法置空可能导致"用户主动删除消息 / 清空会话"等本地删除行为一并失效。接手项目时应实测这一点；若要精确化，可在方法内判断是否处于撤回上下文后再决定是否放行原实现。

### 2.2 撤回处理实现（原文，节选）

```objc
/**
 hook 微信撤回消息

 */
- (void)hook_onRevokeMsg:(id)msgData {
    if (![[TKWeChatPluginConfig sharedConfig] preventRevokeEnable]) {
        [self hook_onRevokeMsg:msgData];
        return;
    }
    id msg = msgData;
    if ([msgData isKindOfClass:objc_getClass("MessageData")]) {
        msg = [msgData valueForKey:@"msgContent"];
    }
    if ([msg rangeOfString:@"<sysmsg"].length <= 0) return;

    //      转换群的 msg
    NSString *msgContent = [msg substringFromIndex:[msg rangeOfString:@"<sysmsg"].location];

    //      xml 转 dict
    XMLDictionaryParser *xmlParser = [objc_getClass("XMLDictionaryParser") sharedInstance];
    NSDictionary *msgDict = [xmlParser dictionaryWithString:msgContent];

    if (msgDict && msgDict[@"revokemsg"]) {
        NSString *newmsgid = msgDict[@"revokemsg"][@"newmsgid"];
        NSString *session =  msgDict[@"revokemsg"][@"session"];
        msgDict = nil;

        NSMutableSet *revokeMsgSet = [[TKWeChatPluginConfig sharedConfig] revokeMsgSet];
        //      该消息已进行过防撤回处理
        if ([revokeMsgSet containsObject:newmsgid] || !newmsgid) {
            return;
        }
        [revokeMsgSet addObject:newmsgid];

        //      获取原始的撤回提示消息
        MessageService *msgService = [[objc_getClass("MMServiceCenter") defaultCenter] getService:objc_getClass("MessageService")];
        MessageData *revokeMsgData = [msgService GetMsgData:session svrId:[newmsgid integerValue]];
        if ([revokeMsgData isSendFromSelf] && ![[TKWeChatPluginConfig sharedConfig] preventSelfRevokeEnable]) {
            [self hook_onRevokeMsg:msgData];
            return;
        }
        NSString *msgContent = [[TKMessageManager shareManager] getMessageContentWithData:revokeMsgData];
        NSString *newMsgContent = [NSString stringWithFormat:@"%@ \n%@",TKLocalizedString(@"assistant.revoke.otherMessage.tip"), msgContent];
        MessageData *newMsgData = ({
            MessageData *msg = [[objc_getClass("MessageData") alloc] initWithMsgType:0x2710];
            [msg setFromUsrName:revokeMsgData.toUsrName];
            [msg setToUsrName:revokeMsgData.fromUsrName];
            [msg setMsgStatus:4];
            [msg setMsgContent:newMsgContent];
            [msg setMsgCreateTime:[revokeMsgData msgCreateTime]];
            msg;
        });

        [msgService AddLocalMsg:session msgData:newMsgData];
    }
}
```

### 2.3 这几段原文带来的三个确定结论

1. **`MessageService` 类是真的**；但用户最初给的 `%hook MessageService / - (void)RevokeMsg:(id)arg1` **方法名是错的**。真实方法名：
   - 微信 < 2.3.22（macOS）：`-onRevokeMsg:`
   - 微信 ≥ 2.3.22（macOS）：**`-FFToNameFavChatZZ:`** ← **这是"新版微信把方法名混淆掉"的硬证据**
2. **撤回系统消息的协议在 macOS 与 iOS 上是一致的**：都是 `<sysmsg>` 包着 `revokemsg`，里面取 `newmsgid` 和 `session`。iOS 侧的 itenfay 用正则从 `m_nsContent` 里抠，macOS 侧用 `XMLDictionaryParser` 解析，指向同一份数据。
3. **"伪造 tip"的做法在两端同构**：`msgType 0x2710` + 状态 `4` + `AddLocalMsg:`。说明这是微信本地系统提示消息的通用表示。

## 3. 【新】macOS 微信 4.x 的完整机制（含"闪退"真正的根因）

来源：`zengtianli/WeChatTweak` 的 README 被完整贴在 issue 里 —— <https://github.com/zengtianli/WeChatTweak/issues/4>（另外该 fork 在 sunnyyoung 上游 issue #1038 里被作者推荐：<https://github.com/sunnyyoung/WeChatTweak/issues/1038>）

### 3.1 撤回到底发生在哪一层（原文转述）

> 撤回不是本地行为——对方点撤回后，服务器给你的客户端推一条 `revokemsg` 指令，客户端的 `parseRevokeXML`（在 `wechat.dylib` 里）解析它，然后执行「删掉本地这条消息 + 插入撤回提示」。**消息本来已经在你本地了**，撤回是事后叫客户端去删它。

- 微信 4.x 把消息逻辑从主二进制**搬到了 `Contents/Resources/wechat.dylib`**。
- 关键函数：`MessageSystemExtInfo::TryParseMessageXML`（补丁点处判断「这条 msgType 是不是 `revokemsg`」）、`parseRevokeXML`。

### 3.2 补丁手法（原文）

```
488319c: bl   0x4431b58      ; 判断这是不是要执行的撤回，结果放 w0
48831a0: cbz  w0, 0x488339c   ; w0==0 才跳过删除；正常 w0≠0 → 往下执行删消息
```

> 把 `cbz w0, X`（`E00F0034`，条件跳转）改成 `b X`（`7F000014`，无条件跳转），跳转目标不变，于是无论如何都跳过删除逻辑。

另一种变体 `keeptip`（消息留下**且**保留撤回提示）：让解析器照跑，只把「要删哪条」的 `newmsgid` 在写入结构体那一刻**改写为 0**（`str x0` → `str xzr`，例如 `60E600F9` → `7FE600F9`），下游按 `newmsgid` 删本地消息时找不到目标。

**定位方式（不依赖方法名的另一种形态）**：靠几何签名在 arm64 切片里唯一定位 —— `parseRevokeXML` 入口 `E` 满足 `E+0x270` 是 `cbz w0`、`E+0x270+delta` 是 `str <Xt>,[x19,#newmsgid]`。已归纳**三代**签名（`cbz` 原字节 / `newmsgid` 字段偏移 / keeptip 的 delta = `0x794` 或 `0x7a0`）。参考实现：<https://github.com/fzlzjerry/wechat-antirecall>

### 3.3 ⚠️ "打完补丁闪退"的真正根因（对 iOS 同样有参考价值）

来自该 README 的 FAQ（原文）：
> **打完补丁微信闪退 / 打不开（269579 起多人报告，#1038）**：2026-09-02 之前的版本重签名时把整个包的 entitlements 全抹掉了（沙盒、相机、麦克风、app-group、Team ID 全没），**SIP 开启的 Mac 上 AMFI 直接把微信杀掉**。

> 注意：**SIP 关闭时坏包照样能开**，所以"微信打得开"不构成任何证据。

**这条对 iOS 侧的映射（我的推断）**：iOS 上同理，重签名后 entitlements 缺失/被改，系统与 App 自身的完整性校验都可能直接让进程起不来。**"闪退"很可能根本不是 hook 写错了，而是签名/entitlements 环节出了问题**——这比"方法名找不到"更常见，也更难查。

### 3.4 其它要点

- 微信**自动更新（整包替换）会把补丁静默抹掉**，社区里"防撤回用着用着又没了"多为此因。
- App Store 版**没有** `XAppUpdateManager`（由 App Store 负责更新），因此"阻止更新"那一步要能跳过而不是报错。
- macOS 侧生态：`zengtianli/WeChatUnrevoke`（GUI）、`MustangYM/SovietExtension`、`a244573118/WeChatIntercept`、`lerry903/WeChat-Anti-Revoke-For-Mac`。

另外两点建议：

1. **不要把 `MessageService` + `RevokeMsg:` 当作有效候选**——它源于一份流传的 hook 清单，本次核对在**任何原文里都没出现**，属于以讹传讹；保留它只会浪费匹配次数。
2. 在 8.0.75 的二进制里**主动搜符号/字符串**：`parseRevokeXML`、`MessageSystemExtInfo`、`TryParseMessageXML`、`revokemsg`、`newmsgid`。macOS 4.x 已证实撤回解析收敛到 `parseRevokeXML` 一带；如果 iOS 8.0.75 也有同名/近名符号（C++ 符号常带），就能拿到一个**比 ObjC 方法名稳定得多**的锚点 —— 顺带说，项目里已有 `tools/analyze_wechat.py` 和 `ipa/微信_8.0.75.ipa`，完全有条件直接验证。
