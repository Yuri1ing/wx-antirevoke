## 0. 调研方法与网络限制（先读，影响可信度判断）

本次调研过程中目标网络环境出现较强的访问限制，必须提前说明，否则会误判"证据强度"：

| 通道 | 状态 | 说明 |
|---|---|---|
| `raw.githubusercontent.com` | ❌ 不可达 | `web fetch failed` |
| `github.com` 网页 | ❌ 中途起不可达 | `URL hostname "github.com" resolves to a non-public IP address` |
| `api.github.com` | ⚠️ 时好时坏 | 前半程正常（HTTP 200），后半程 DNS 解析失败 |
| `cdn.jsdelivr.net` / `data.jsdelivr.com` | ✅ 可用 | 本报告大部分源码/文件树通过它取得 |
| `r.jina.ai`、`raw.githack.com`、`statically.io` | ❌ 不可达 | |
| `grep.app` | ❌ 429 / Vercel 校验 | 未能用于代码检索 |

**因此：**
- 「源码原文」主要通过 **GitHub Contents API**（返回 base64）解码获得，少量通过 jsDelivr 取得。
- jsDelivr 对 `.xm`（被识别为 `audio/xm`）和部分 `.m`（`application/octet-stream`）**拒绝返回**，导致若干仓库的 hook 源码**未能取到原文**。这些地方我会明确写"未取到原文"，不会用推测补齐。
- 本报告**没有**任何"我编造的方法名/类名"。凡是无法查证的，一律写成"未找到证据"。

## 2. 这些项目里防撤回到底 hook 了什么

### 2.1 iOS：`itenfay/WeChat_tweak` —— `%hook CMessageMgr` / `- (void)onRevokeMsg:`

这是**本次调研唯一取到完整原文的 iOS 防撤回实现**。

- 来源文件：[`WeChatPluginDev/wapleodtcorexpc/src/Tweak.xm`](https://github.com/itenfay/WeChat_tweak/blob/master/WeChatPluginDev/wapleodtcorexpc/src/Tweak.xm)
- 取法：GitHub Contents API base64 解码（原文可复核：`https://api.github.com/repos/itenfay/WeChat_tweak/contents/WeChatPluginDev/wapleodtcorexpc/src/Tweak.xm`）
- 文件大小 18752 字节，SHA `9046616b5e9d714f5ab2c427499fc49324da9acd`

**原文片段（防撤回部分）：**

```objc
%hook CMessageMgr

- (void)onRevokeMsg:(CMessageWrap *)arg1 {
	if (![WCPLRedEnvelopConfig sharedConfig].revokeEnable) {
		%orig;
	} else {
		if ([arg1.m_nsContent rangeOfString:@"<session>"].location == NSNotFound) { return; }
		if ([arg1.m_nsContent rangeOfString:@"<replacemsg>"].location == NSNotFound) { return; }

		NSString *(^parseSession)() = ^NSString *() {
			NSUInteger startIndex = [arg1.m_nsContent rangeOfString:@"<session>"].location + @"<session>".length;
			NSUInteger endIndex = [arg1.m_nsContent rangeOfString:@"</session>"].location;
			NSRange range = NSMakeRange(startIndex, endIndex - startIndex);
			return [arg1.m_nsContent substringWithRange:range];
		};

		NSString *(^parseSenderName)() = ^NSString *() {
		    NSRegularExpression *regex = [NSRegularExpression regularExpressionWithPattern:@"<!\\[CDATA\\[(.*?)撤回了(一条)?消息\\]\\]>" options:NSRegularExpressionCaseInsensitive error:nil];

		    NSRange range = NSMakeRange(0, arg1.m_nsContent.length);
		    NSTextCheckingResult *result = [regex matchesInString:arg1.m_nsContent options:0 range:range].firstObject;
		    if (result.numberOfRanges < 2) { return nil; }

		    return [arg1.m_nsContent substringWithRange:[result rangeAtIndex:1]];
		};

		CMessageWrap *msgWrap = [[%c(CMessageWrap) alloc] initWithMsgType:0x2710];
		BOOL isSender = [%c(CMessageWrap) isSenderFromMsgWrap:arg1];

		NSString *sendContent;
		if (isSender) {
			[msgWrap setM_nsFromUsr:arg1.m_nsToUsr];
			[msgWrap setM_nsToUsr:arg1.m_nsFromUsr];
			sendContent = @"你撤回了一条消息";
		} else {
			[msgWrap setM_nsToUsr:arg1.m_nsToUsr];
			[msgWrap setM_nsFromUsr:arg1.m_nsFromUsr];

			NSString *name = parseSenderName();
			sendContent = [NSString stringWithFormat:@"拦截 %@ 的一条撤回消息", name ? name : arg1.m_nsFromUsr];
		}
		[msgWrap setM_uiStatus:0x4];
		[msgWrap setM_nsContent:sendContent];
		[msgWrap setM_uiCreateTime:[arg1 m_uiCreateTime]];

		[self AddLocalMsg:parseSession() MsgWrap:msgWrap fixTime:0x1 NewMsgArriveNotify:0x0];
	}
}

%end
```

**这段代码说明了什么（事实层面）：**

1. **真正的 hook 点是 `-[CMessageMgr onRevokeMsg:]`**，参数是 `CMessageWrap *`。注意：**不是** `HandleRevokeMsg:`，也不是 `MessageLogicController`。
2. 原文里能看到微信撤回消息的**内部协议格式**：`m_nsContent` 里带 `<session>…</session>` 和 `<replacemsg>…</replacemsg>`，发送者名字藏在 `<!\[CDATA\[XXX撤回了(一条)?消息\]\]>` 里。
3. 插件的手法不是"阻止删除"，而是**丢弃原方法（不调用 `%orig`），自己伪造一条 `msgType = 0x2710`（本地 tip 消息）插回会话**：
   - 对方撤回 → 插入"拦截 XXX 的一条撤回消息"
   - 自己撤回 → 插入"你撤回了一条消息"
   - `setM_uiStatus:0x4` 是把它标成系统/居中提示
   - `AddLocalMsg:MsgWrap:fixTime:0x1 NewMsgArriveNotify:0x0` 落库并静默插入
4. 同文件里还有另外两个防撤回相关 hook（也是 `CMessageMgr`）：

```objc
- (id)GetMsgByCreateTime:(id)arg1 FromID:(unsigned int)arg2 FromCreateTime:(unsigned int)arg3
        Limit:(int)arg4 LeftCount:(unsigned int *)arg5 FromSequence:(unsigned int)arg6 {
	id result = %orig;
	WCPLRedEnvelopConfig *config = [WCPLRedEnvelopConfig sharedConfig];
	if (config.chatIgnoreInfo[arg1].boolValue) {
		return [WCPLFuncService filterMessageFromMsgList:result];
	}
	return result;
}
```

```objc
%hook SyncCmdHandler

- (_Bool)BatchAddMsg:(_Bool)arg1 ShowPush:(_Bool)arg2 {
	NSMutableArray *msgList = [self valueForKey:@"m_arrMsgList"];
	NSMutableArray *msgListResult = [WCPLFuncService filterMessageFromMsgList:msgList];
	[self setValue:msgListResult forKey:@"m_arrMsgList"];
	return %orig;
}

%end
```

> 这两个是"屏蔽消息"功能的 hook，不是防撤回本身，但**它们揭示了微信消息落库前会经过 `SyncCmdHandler` 的 `m_arrMsgList`**——这是做"数据层拦截"的候选点。

### 2.2 与用户列出的历史 hook 点的核对结果

| 用户列出的 hook 点 | 本次调研结果 |
|---|---|
| `%hook CMessageMgr` / `- (void)HandleRevokeMsg:(id)arg1` | ❌ **未找到任何出处**。取到原文的 iOS 实现用的是 `- (void)onRevokeMsg:(CMessageWrap *)arg1` |
| `%hook MessageService` / `- (void)RevokeMsg:(id)arg1` | ⚠️ **类名对、方法名错**（GitHub 恢复后已补取 macOS TKkk 源码原文证实，见 `调研补充-补取源码与新版证据.md`）：类确为 `MessageService`，旧版方法名是 `onRevokeMsg:`，**≥ macOS 微信 2.3.22 起被混淆为 `FFToNameFavChatZZ:`**。`RevokeMsg:` 这个拼法**在任何原文里都没出现** |
| `MessageLogicController` / `BaseMsgContentLogicController` 的 `onRevokeMsg:` | ⚠️ 部分相关：itenfay 的 Tweak.xm **确实 hook 了 `BaseMsgContentViewController`**，但只用于取当前联系人（`GetContact` / `m_nsUserName`），**与防撤回无关** |
| `WCRemoteMessage` | ❌ 未找到任何出处 |

> **结论（事实）**：这次能确证的 iOS hook 点只有 `-[CMessageMgr onRevokeMsg:]`。你手上的另外几个类名/方法名，在本轮可访问的材料里**一个都没有佐证**；不能确认它们是真存在过，还是被以讹传讹。

### 2.3 macOS：已经**不是 hook** 了 —— 而是二进制字节补丁

这一点对判断 iOS 未来走向非常重要。

`sunnyyoung/WeChatTweak`（13840 stars，macOS）当前 master 分支的文件树**只有 4 个 Swift 文件**（`main.swift` / `Command.swift` / `Config.swift` / `Patcher.swift`）加一个 6265 字节的 `config.json`，**没有任何 Logos/Swift hook 代码**：

- [`config.json`](https://github.com/sunnyyoung/WeChatTweak/blob/master/config.json)
- [`Patcher.swift`](https://github.com/sunnyyoung/WeChatTweak/blob/master/Sources/WeChatTweak/Patcher.swift)（原文未取到，CDN 返回 octet-stream）

`config.json` 原文片段：

```json
[
  {
    "version": "31927",
    "targets": [
      {
        "identifier": "revoke",
        "entries": [
          { "arch": "arm64", "addr": "103dba3d0", "asm": "00008052C0035FD6" }
        ]
      },
      {
        "identifier": "multiInstance",
        "entries": [
          { "arch": "arm64", "addr": "1001e1c10", "asm": "20008052C0035FD6" }
        ]
      }
    ]
  },
  { "version": "34371", "targets": [ { "identifier": "revoke", "entries": [
      { "arch": "arm64", "addr": "103e7cd2c", "asm": "00008052C0035FD6" } ] } ] }
]
```

**解读（事实 + 明确标注的解读）：**
- 事实：补丁做法是"按微信 build 号 + 绝对文件偏移 + 架构"写入固定 4/8 字节机器码。
- 解读（ARM64 指令语义，属我的分析）：`00008052` = `MOV W0, #0`，`C0035FD6` = `RET`。即**把撤回处理函数整个改成"返回 0 直接返回"**。`20008052` = `MOV W0, #1`，用于多开开关。
- **重要**：一个 13840 stars 的项目在 macOS 4.x 上**放弃了 Objective-C hook、改用字节补丁**——这本身是"hook 路线在新版微信上受挫"的强信号（**这是我的推断，不是原作者声明**）。

## 3. 有没有针对 8.0.5x / 8.0.6x / 8.0.7x 仍然可用的防撤回实现？

**明确回答：没有找到。**

- 在 GitHub 仓库搜索（`wechat revoke`、`wechat tweak ios`、`WeChatPlugin-iOS` 等多组关键词）中，**没有任何 iOS 项目声明支持 iOS 微信 8.0.5x/6x/7x**。
- 「新版仍在维护」的项目全部是 **macOS 或 Windows**：
  - macOS [X1a0He/X1a0HeWeChatPlugin](https://github.com/X1a0He/X1a0HeWeChatPlugin) v2.10.0（2026.09.19），支持到微信 macOS 4.1.15.20(270100)；
  - macOS [sunnyyoung/WeChatTweak](https://github.com/sunnyyoung/WeChatTweak) 的补丁表更新到 build 34371；fork [zengtianli/WeChatTweak](https://github.com/zengtianli/WeChatTweak) 自述覆盖 `268575→269627`；
  - Windows [huiyadanli/RevokeMsgPatcher](https://github.com/huiyadanli/RevokeMsgPatcher)。
- **它们 hook / patch 什么？**
  - macOS 两项都已转向"**定位函数入口 → 写 `MOV W0,#0; RET`**"的字节补丁模式（`config.json` 为证），而不是 hook 某个 ObjC 方法名。
  - Windows 的 RevokeMsgPatcher 是 hex patch `WeChatWin.dll` 中的撤回分支。

> ⚠️ **不要把这些 macOS 微信的版本号（4.1.15.20）当成 iOS 微信的 8.0.x**，两者是完全独立的产品线。

## 4. 微信 8.0.x 的反注入 / 反调试 / 越狱检测

### 4.1 结论先行

**有，而且成体系。** 本轮调研找到了**两组、可互相印证**的证据：一组是**老代码里直接出现微信的越狱检测类**，另一组是**2026 年对微信 iOS 反作弊体系的完整逆向分析**（列出了类名与方法名）。

### 4.2 证据一：微信内置 `JailBreakHelper`（老版本即已存在）

来源：`itenfay/WeChat_tweak` 的 `Tweak.xm`（与 2.1 同一文件），原文：

```objc
%hook JailBreakHelper

+ (_Bool)JailBroken {
	return NO;
}

- (_Bool)IsJailBreak {
	return NO;
}

- (_Bool)HasInstallJailbreakPlugin:(id)arg1 {
	return NO;
}

- (_Bool)HasInstallJailbreakPluginInvalidIAPPurchase {
	return NO;
}

%end
```

**事实层面**：
- 微信里存在名为 `JailBreakHelper` 的类，方法名包括 `+JailBroken`、`-IsJailBreak`、`-HasInstallJailbreakPlugin:`、`-HasInstallJailbreakPluginInvalidIAPPurchase`。
- 插件作者必须显式把这些**全部返回 NO**，且要**同时**把它们写进 hook——这暗示微信内部会**多处交叉调用**这些检测。
- 该源码时间较早（对应微信 7.x 前后），说明**越狱检测不是 8.0.x 才引入的**。

### 4.3 证据二：2026 年对微信 iOS 反作弊 6 层体系的逆向（含类名/方法名）

来源：看雪论坛精华文章《逆向反封号 dylib：OLLVM CFF/MBA 混淆拆解与 167 个 Hook 实例分析》（作者 qqqiu，2026-05-26），转载页：<https://yunpan.plus/t/25392-1-1>

> 说明：该文分析的是一个**第三方商业"反封号" dylib（`JiDe.dylib`）**，文中列出的方法名是**这个 dylib 去 hook 的微信侧目标**，因此可反推微信存在这些类与方法。文中未明确写微信的具体版本号。

文章给出的对照表（原文摘录，**这些是微信侧的类/方法**）：

| 微信侧防御层 | 类 / 方法（原文） |
|---|---|
| ① 环境信任检测 | `MMRuntimeIntegrity`：`isJailbrokenDevice`、`isEnvironmentTrusted`、`auditLoadedImages` |
| ② 签名 / 完整性校验 | `MMSecurityPolicyValidator`：`verifyCodeSignature:`；`CUtility`：`validateCertChain:`、`getAppBundleSignatureHash`、`integrityHash` |
| ③ 反篡改监控 | `MMAntiTamperGuard`：`startMonitoring`、`refreshPolicyStore` |
| ④ 事件上报通道 | `MMTokenService`：`flushSecurityEvents`、`reportCrashLog:type:`、`reportDeviceToken:`、`refreshTokenWithPolicy:` |
| ⑤ A/B 配置开关 | `ExptService`：`getBoolExpt:`，key 为 `clicfg_gogwcs_ios_runtime_sdk_dc_dc_report_enable`、`clicfg_gogwcs_ios_runtime_sdk_main_cert_chain_report` |
| ⑥ 状态字典 + 核心动作 | 字典 key：`jb_indicator`、`env_abnormal`、`cert_valid`；`MMContext`：`startVerifyContact:opcode:verifyMsg:` |

文章里几句关键的原文（可直接引用）：

- 关于加载镜像审计：
  > "扫一遍 dyld 已加载的所有 image，看有没有 MobileSubstrate / Cydia / Theos 这种越狱痕迹"。dylib 把它 hook 成"过滤掉自己"——**作者没有简单粗暴地让 `auditLoadedImages` 返回空，而是返回一个"过滤后的真实列表"，因为返回空会立即触发风控**。
- 关于完整性校验：
  > "当微信调用 `integrityHash` getter 时，dylib hook 这个 getter，直接返回这个 SHA-256("") 伪值"；"**任何 hash 校验如果不绑定数据，等于摆设**"。
- 关于为什么还要 hook A/B 开关（第 ⑤ 层）：
  > "只 nullify ④ 的代价：…服务端可以从其他接口反查'环境检测是否触发'。hook ⑤ 的优势：让微信自己决定不调用上报。客户端代码路径 100% 走'不需要上报'分支…**服务端没有任何'客户端被 hook'的反向指纹**。"

**这直接回答你的问题 4：**
- 微信 iOS **有**反注入 / 完整性校验 / 越狱检测，且不止一个类：`MMRuntimeIntegrity`、`MMSecurityPolicyValidator`、`CUtility`、`MMAntiTamperGuard`、`MMTokenService`、`ExptService`。
- 检测内容包括：dyld 已加载镜像列表（找 Substrate/Cydia/Theos 痕迹）、代码签名校验、证书链校验、bundle 签名 hash、运行时完整性 hash。
- 检测结果**不是本地弹窗，而是通过独立上报通道（`MMTokenService`）打到服务端**——这与"插件只在本地生效就没事"的直觉相反。

### 4.4 `ptrace` / `Frida` 检测

- **未找到**关于微信 iOS 自身调用 `ptrace(PT_DENY_ATTACH)` 或主动检测 Frida 的公开证据。
- 文章提到 Frida 时是**站在攻击方**说的："如果有越狱设备 + frida，破这个 30 秒搞定"。
- **不要把这一点写成事实。** （推测：`MMRuntimeIntegrity.auditLoadedImages` 这类镜像审计在 iOS 上足以覆盖 Frida gadget 的常见注入形态，但不等于存在专门的 Frida 检测代码。）

### 4.5 用轻松签这类工具注入 dylib 的实际风险

**事实（有来源）：**
1. **重签后必须改签名与 entitlements**。itenfay 的 README 明确列出要删除多个 `Entitlements_*.plist`、重签 app 与全部 framework/dylib（`codesign -f -s "..."`），并强调删除 `_CFBundleDisplayName`、`build_time/by/path/rev/tag/uuid/ver` 等 Info.plist key —— 说明**重签会显著改变 bundle 特征**。
   来源：<https://github.com/itenfay/WeChat_tweak/blob/master/README.md>
2. **闪退是真实现象**。[Taosky/unsigned-ipa-cn](https://github.com/Taosky/unsigned-ipa-cn) README 原文：
   > "**Feather签名微信有闪退问题的可以试试这个**"（指轻松签/esign）
   即：签名工具与微信之间存在兼容性问题，社区用"换签名工具"来绕。
3. **封号**。[LINUX DO：WAuxiliary模块/IOS拉闸，微信大规模封号](https://linux.do/t/topic/964786)（标题级证据，正文因网络限制未能读取）。另有 itenfay README 自述免责声明："当使用本插件时，请使用者自行承担各种状况，包括但不限于'禁用红包功能'以及'**微信封号**'。"

**我的推断（明确标注为推断）：**
- 一旦 dylib 被注入，`verifyCodeSignature:` / `getAppBundleSignatureHash` / `integrityHash` 三个校验点里**至少有一个会受影响**（重签改变了签名与二进制内容）；`auditLoadedImages` 则会多看到一个非系统 image。若插件不主动处理这些（商业"反封号" dylib 才做这些），就相当于**把风险全暴露给服务端**。
- 因此"本地不联网就安全"的判断是**错的**——上报通道独立于业务接口。

## 5. 有没有"不依赖具体方法名"的通用思路？

### 5.1 有据可查的实例：字节级补丁（macOS）

macOS `sunnyyoung/WeChatTweak` 的 `config.json` 就是**完全不依赖方法名**的方案：
- 不写 `%hook`，不提 ObjC 类名/方法名；
- 只依赖 **build 号 → 文件偏移 → 期望字节**；
- fork（zengtianli）还加了 "verifies original bytes before writing"（写前校验原字节）与重签名保留 entitlements。

**评价**：最稳（不受方法改名影响），但**最不通用**——微信每次发版，偏移全变，必须人工重新定位。这也是为什么它需要为每个 build 号维护一条记录。对 iOS 而言还多一重障碍：**iOS 主二进制被重签后完整性校验更难过**。

### 5.2 运行时枚举 + 模式匹配动态 hook

- 通用技术本身是成熟的：`objc_getClassList` / `class_copyMethodList` 遍历，对命中的 `SEL` 用 `MSHookMessageEx` / `method_setImplementation` 动态替换。
- **但：本轮调研没有找到任何在 iOS 微信上这么做的公开实践记录。** GitHub 上现存 iOS 项目全部是写死的 `%hook 类名`。因此：
  - 我不能给你"别人这么干并且成功"的证据；
  - 也不能给你"这么干会失败"的证据。
- **风险（我的推断，非事实）**：
  1. **误伤**：微信消息类方法命名高度重复（`onXxx:`/`handleXxx:`），按子串匹配容易挂到热路径上；
  2. **性能**：`CMessageMgr` 的消息回调是高频路径，全量枚举+逐个 hook 会有启动开销；
  3. **反噬**：即使 hook 成功，`MMAntiTamperGuard` / `auditLoadedImages` 的检测并不会因为你"用动态方式 hook"而消失——**绕方法名 ≠ 绕检测**；
  4. **类名/方法名是否真被混淆，本轮没有证据**。不能假设 8.0.75 "改名了"。

**结论**：如果你要在 8.0.75 上做不依赖方法名的方案，**真正需要动态化的是"定位 hook 点"这一步，而不是规避检测**。检测层必须单独处理（见第 4 节）。

- **补丁/插件与微信版本不匹配** —— RevokeMsgPatcher 每个微信版本都要单独适配（issue #1014 就是用户版本没对上）。

- iOS 8.0.5x+ 防撤回失效，最可能的原因不是"`onRevokeMsg:` 被改名"，而是：

  2. 撤回逻辑**可能不再只走 `CMessageMgr.onRevokeMsg:` 这一条路**（例如新增的撤回路径/服务端下发），单点 hook 拦不住；
  3. 微信 iOS 的完整性/环境校验在较新版本上更活跃，导致**注入后被风控甚至踢下线**（第 4 节证据支持"有检测"，但"检测是失效主因"仍是推断）。

## 7. 给「iOS 微信 8.0.75 防撤回」的结论与建议

### 7.1 结论

1. **公开生态是断层的**：iOS 侧最新公开源码停在 2021/2024 年，且**没有任何项目声称支持 8.0.5x 以上**。macOS 侧反而很活跃，但已在 2025–2026 转向**字节补丁 + 重签名**（不用 hook）。
2. **唯一可信的 iOS hook 点（有原文）**是 `-[CMessageMgr onRevokeMsg:]`，配合 `CMessageWrap` 的 `<session>/<replacemsg>/CDATA` 格式，把撤回改写成一条 `msgType 0x2710` 的本地 tip。
3. **微信 iOS 有明确的多层检测**：`JailBreakHelper`（老）+ `MMRuntimeIntegrity` / `MMSecurityPolicyValidator` / `CUtility` / `MMAntiTamperGuard` / `MMTokenService` / `ExptService`（新，2026 年逆向）。**检测结果会上报服务端。**
4. **因此 8.0.75 的真正难点不是"找不到方法名"，而是"注入后如何不被完整性/环境检测打掉"。** 商业"反封号 dylib"的存在本身，就是这个问题真实且昂贵的证据。

### 7.2 如果要做（以下全部为建议/推断，风险自负）

- **先验证可行性再写功能**：在 8.0.75 的砸壳二进制上先确认 `CMessageMgr` 是否仍存在、`onRevokeMsg:` 的 selector 是否仍被实现（class-dump / `class_copyMethodList` 即可），**再决定是否沿用老代码**。不要直接套 2019 年的 `Tweak.xm`。
- **hook 层只做业务，检测层单独处理**：至少需要评估 `MMRuntimeIntegrity.auditLoadedImages`、`CUtility.integrityHash`、`MMSecurityPolicyValidator.verifyCodeSignature:` 三个点，并注意 `MMTokenService` 的上报是独立通道。
- **签名侧别踩坑**：优先 TrollStore / LiveContainer 这类**不破坏原签名**的路径（Taosky README 明确区分了 TrollStore / 自签 / 证书签名 / 轻松签 的差异）；证书重签（轻松签/Feather）已有"微信闪退"的社区记录。
- **务实的期望管理**：在没有完整处理检测层的情况下，**防撤回能用 ≠ 账号安全**；签名注入+上报存在 = 被风控只是时间问题。
